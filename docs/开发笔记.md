> 启动方式：双击 `D:\crawl_analyst\start_redis.cmd`，或 `start_all.cmd` 会自动带起来。
> 这个 Windows 构建对盘符敏感，必须 `cd /d D:\Redis8` 后用相对路径传配置文件，否则报
> `can't open config file '/Redis8/D:\Redis8\...'`。
>
> Python 客户端锁在 `redis==6.4.0`：kombu 5.7 要求 ≥6.1，而 redis-py 8.x 会强发 `HELLO 3`，本机若连回老 6379 会报 `unknown command HELLO`。6.4 兼容两边，是当前最稳的版本。

**三个 Celery 任务**

| 任务名 | 做什么 | 成本 |
|---|---|---|
| `crawl.collect` | 采集 + 清洗 + 增量入库 | 低（只抓网页） |
| `crawl.analyze` | 读库 → LIDA 出图 | 高（调大模型） |

## 七之四、已知的爬取坑（踩过并已处理）

1. **arXiv 响应慢**：实测单页 20~60 秒，默认 60 秒超时直接失败。已把 `page_timeout` 提到 120 秒，并对每个 URL 重试 3 次（间隔 3 秒），失败 URL 记入 `failed_urls` 上报，不静默丢数据。
2. **`AsyncWebCrawler` 参数名是 `config`**：写成 `browser_config=` 会报 `got multiple values for keyword argument 'browser_config'`。
3. **DuckDB 写 pandas**：用 `con.register()` 后 `unregister()` 会报 `ResourceInUseException`（结果集未消费）。改成 replacement scan（直接 `SELECT ... FROM dfw`）即可。
4. **LIDA 图表标题 = goal 文本**：goal 写太长，标题会被截断，所以 goal 要短（20 字左右）。
5. **DuckDB 连接配置必须一致**：同一进程里对同一个 `.duckdb` 文件混用只读和读写连接会报
   `Can't open a connection to same database file with a different configuration`。
   本项目统一用读写连接（`get_con()` 里的 `read_only` 参数只为兼容旧调用保留）。
6. **Redis 8 Windows 构建对盘符敏感**：直接传 `D:\Redis8\xxx.conf` 会被解析成 `/Redis8/D:\Redis8\xxx.conf` 报找不到文件，
   必须 `cd /d D:\Redis8` 后用相对路径 `redis-6380.conf` 启动；配置里的 `dir`/`logfile` 也要用正斜杠。

## 七之五、增量监控（“网站更新→数据自动更新”的实现）

```powershell
python src\monitor_svc.py --category cs.AI --rounds 1     # 检查一轮
python src\monitor_svc.py --category cs.AI,cs.LG --interval 600   # 每 10 分钟轮询
python smoke_test_monitor.py                              # 三轮验证逻辑
```

两层机制，互不依赖：

| 机制 | 做什么 | 成本 |
|---|---|---|
| **内容指纹** `content_fingerprint()` | 把页面所有 `paper_id` 排序后做 sha256，存进 `watch_state` 表；和上次比对，判断“页面变没变” | 一次哈希 |
| **主键差集** `get_existing_ids()` | 不管指纹，拿本次 `paper_id` 和库里已有集合做差，只 `INSERT` 新增行 | 一次集合运算 |

指纹决定“要不要重新调大模型分析”（贵），差集保证“数据一定准”（便宜）。任何一层失效都不会污染数据。

实测三轮结果：第 1 轮首次识别为有更新 → 第 2 轮判定无变化、跳过分析（省钱）→ 手动删 3 条后第 3 轮精准补回 3 条。

## 七之六、通用网址流程（本轮改造，前端已重写）

原来的流程只认 arXiv。现在的主线是**输入任意公开网址 → 自动抽取结构 → 自动摘要 → 自动/指定分析目标 → 出图**，arXiv 只是其中一个自动命中的适配器。

**页面上的三个输入**

| 输入 | 填 | 不填 |
|---|---|---|
| 网址 | 必填，`https://` 会自动补 | — |
| 分析目标 | 原样作为图表标题，例如「各价格区间的书籍数量分布」 | 由 `propose_goals()` 让大模型按抽到的字段自动提 3 个，取第一个出图；大模型不可用时用 `default_goal()` 规则兜底 |

**三级抽取（能用的最强那一级优先）**

| 顺序 | 函数 | 判据 | 产出 |
|---|---|---|---|
| 1 | `extract_arxiv()` | URL 命中 `arxiv.org/list/` | 论文编号/标题/作者数/主分类/月份/标题字数/有开源代码 |
| 2 | `extract_tables()` | 页面有 `<table>`，≥2 行 ≥2 列 | 表格直接变 DataFrame，表头不合格就用「列N」 |
| 3 | `extract_repeated_items()` | 同签名元素（tag+class）出现 ≥8 次、平均文本 15~500 字 | 条目标题/标题字数/条目长度/链接/价格/评分 |
| 4 | `extract_text_blocks()` | 以上都没有 | 按 Markdown 标题切块：章节/字数/行数/段落数 |

抽完还要过两道治理：

- `polish()`：丢全空列、丢 list/dict 列、≥70% 可转数值的列转数值（价格 `£51.77 → 51.77`）、限 300 行 12 列
- `analysis_view()`：把「链接/URL、以及唯一率高且平均长度 ≥25 的列」从**分析视图**里剔掉，避免大模型生成「各链接数量分布」这种没意义的图（落盘和预览里这些列仍然保留）

**一次出多张图（`analyze_multi_goals`）**

`analyze_dataframe()` 只画一张图。要多图正确做法不是调 N 次它——那样 N 个目标 = N 次 summarize + N 次 visualize，翻倍烧 token。新增的 `analyze_multi_goals()` 把 **summarize 只做一次、visualize 按目标各做一次**，N 个目标只多花 N 次 visualize：

```python
_, charts, errs = analyze_multi_goals(df, goals[:3], library="seaborn", prefix=f"page_{page_id}")
```

图表命名 `page_<page_id>_g<i>_<j>.png`（第 i 个目标第 j 张图），文件名不冲突也不覆盖。上限由 `.env` 的 `PAGE_MAX_CHARTS` 控制（默认 3）。

**分析目标过滤（`sanitize_goals`）**：大模型偶尔会提「不同标题字数的价格占比」这种数据上站不住的图（对连续数值求占比没有业务含义）。这里用确定性规则兜底，不靠模型自觉：

- 目标里出现「趋势 / 环比 / 同比」→ 丢（这批数据没有时间列）
- 目标同时命中数值字段名 + 「占比 / 比例 / 百分比 / 增长率」→ 丢（只允许「各<类别字段>的数量占比」）
- 过滤后为空 → 回落到 `default_goal()` 的规则目标

实测三个目标过滤前后对比：过滤前第 3 个目标是「不同标题字数书籍的价格占比」（图里 y 轴是每本书价格占总价的份额，纯垃圾），改 prompt + 加规则后变成「各价格区间的条目数量占比」（40% 落在 £50-60，可用）。

**空壳页识别（`detect_blocked`）与正文段落兜底**

用淘宝搜索页实测暴露的问题：抓取成功、但抓到的是「加载中」「亲，请登录」的空壳页（淘宝对无登录态请求返回的就是这个壳，浏览器能看到商品是因为浏览器有 cookie），结果只提示"未抽取到可绘图的结构化数据"——用户分不清是站点拦了还是自己用错了。

两条改动：

| 改动 | 做法 | 效果 |
|---|---|---|
| 空壳页识别 | 扫「加载中 / 请登录 / 扫码登录 / 安全验证 / 验证码 / captcha / just a moment / access denied」等信号，**命中 ≥2 个不同关键词**（或正文 < 1200 字符）才判定，避免"文章里提到 robot"被误判 | 淘宝实测：命中「加载中」+「请登录」→ 判定为空壳 |
| 明确文案 | 空壳页且 extraction 走的是 `text_blocks` 时，直接跳过出图（省 token），提示「抓到的不是数据页：页面显示「加载中」…淘宝/京东/拼多多/小红书需要登录态且有人机校验…换成公开列表页才能出图」 | 用户知道是站点边界，不是 bug |
| 段落兜底 | `extract_text_blocks` 拿不到 3 个章节时，按空行切段落（≥4 段），输出「段落序号 / 字数 / 句数 / 含数字 / 行数」，让长文页也能出图 | 单篇文章实测出图（各段落字数分布 + 平均线） |

前端同时在网址输入框下加了一行前置说明：「只抓不需要登录、没有风控的公开页面」，把边界摆在提交之前。被拦下时，图表区还会直接带一个「换成 books.toscrape 试一次」的按钮，一键把能出图的站点填进输入框，不让用户卡在死路上。

**当当商品适配器（`extract_dangdang`）：国内站点能做到什么程度**

被淘宝挡了几次之后试了国内同类站：**当当分类页 `/cp01.54.00.00.00.00.html` 在不需要登录态时能返回完整列表**，HTML 里商品块是 `li.line1`，价格拆在 `span.search_now_price`（现价）、`span.search_pre_price`（定价）、`span.search_discount`（折扣「7.17折」）里。通用抽取只认连续文本「¥56.60」，被 span 拆开就抽成空值，所以为它单写了一个适配器：

| 抽取字段 | 来源 | 实测 |
|---|---|---|
| 商品标题 / 链接 | `p.name a` | 60 条 |
| 现价 / 定价 | `span.search_now_price` / `search_pre_price` | 60 条全有值，19.8~157.7 元 |
| 折扣 | `search_discount` 的「x 折」 | 22 条缺失（没做活动） |
| 评论数 | `a.search_comment_num` | 59 条 |

**稳定性结论**：这个抽取是一次性成功的，但连续抓 4 次后同一个 IP 开始返回「人机验证」空壳页（551 字符），换 session 也躲不过。所以演示不用当当，只保留代码——它是「适配器分层」最好的例子：同一套流水线，加一个适配器就多认识一个站点，但站点让不让抓是站点说了算。

**中国图书网适配器（`extract_bookschina`）：能稳定演示的中文电商**

找中文电商替身时实测：**中图网 `https://www.bookschina.com/` 不需要登录、不弹验证码**，首页 70 个商品块 `div.bDetai`，书名在 `div.bName a`，到手价 `span.sellPrice`（¥11.7），原价 `span.price`（¥45.0），折扣率自己算。

| 字段 | 实测 |
|---|---|
| 书名 / 链接 | 70 条 |
| 到手价 | 70 条全有值（1.1~308.5 元，中位数 9.8） |
| 原价 / 折扣率 | 70 条，折扣率 = 到手价 / 原价 |
| 出图 | 「统计不同到手价区间的图书数量」端到端成功，中文标签正常 |

**通用商品抽取也顺带修了**（`extract_repeated_items`）：原来只认整块文本里连续的「¥56.60」，价格被 `<span class="price">` 拆开就抽空。现在按三层找价：先找 class/id 含 price/售价/价格 的元素 → 再退回整块文本正则 → 输出 `价格`（数值）+ `币种`（CNY/USD/GBP…）。选块打分也改了：从「条数最多」改成 `条数 × (0.45×标题比例 + 0.45×价格比例 + 0.1×图片比例)`，否则电商站会选中导航菜单（实测孔夫子、Allbirds 都被导航菜单带偏）。

**JSON 接口数据源（`json_api` 适配器）**

微博搜索页 `s.weibo.com/weibo?q=...` 实测抓不到：无登录态时返回 2715 字节纯 JS 壳、可见字符 0 个，crawl4ai 直接判 `Blocked by anti-bot protection: minimal_text, no_content_elements`；crawl4ai 官方云 API 表现为 502 超时（其响应里 `outcome: blank`）。

但微博的**公开 JSON 接口**能取：`https://weibo.com/ajax/side/hotSearch` 返回 51 条热搜，字段 `word / num（热度）/ rank（排名）`。所以给流水线加了一路：

| 环节 | 做法 |
|---|---|
| 探活 | `crawl_any` 先用 `requests` 试一次，`content-type` 含 json 就直接用，不进浏览器（省 7 秒以上） |
| 请求头 | 带同站点 `Referer`（微博接口校验 Referer，裸请求返回 `{"error":"Forbidden"}` 403） |
| 转表 | `json_to_df`：递归找出最长的一组同构对象 → DataFrame；丢掉 URL/颜色/单一值/0-1 常量列，数值列优先，最多 10 列；`word/num/rank` 等常用键改中文列名 |
| 出图 | 实测 51 行、1 张图（「统计各热度区间的热搜话题数量」），端到端成功 |

意义：数据源从「只能爬 HTML 页面」扩到「HTML 页面 + JSON 接口」，面试里可以讲「同一条流水线三种入口：结构表 / 重复卡片 / JSON 接口」。

## 七之七、定时监控（APScheduler，已接入 FastAPI）

回答"网站更新了，数据能不能自己跟着变"这件事：打开页面右上角填网址 → 选间隔 → 点「开启监控」，到点自动抓一次、自动摘要、自动出图，每次快照都进 `pages` 表，历史列表里能看到同一个 URL 的累计快照数。

**为什么放在 FastAPI 进程内而不是 Celery**：到点"检查一个网页"本身是轻量调度动作，真正的重活（抓取+大模型）已经封装在 `run_page()` 里。省一个 beat 进程，笔记本上少一份常驻内存。生产中要更稳可以换成 `celery beat + page_task.delay`，接口和数据表都不用动。

**调度相关代码**（`src/main.py`）

| 函数 / 接口 | 作用 |
|---|---|
| `scheduler = BackgroundScheduler(timezone="Asia/Shanghai")` | 进程内调度器，启动时 `start()` |
| `_watch_job(watch_id)` | 到点执行：`asyncio.run(run_page(url, goal))`，成功与否都 `touch_watch()` 记一次 |
| `_schedule_watch()` | 注册 `interval` 任务，`max_instances=1` + `coalesce=True`，首次执行延后 60 秒 |
| `POST /api/watch` | `{url, goal, minutes}` 开监控，`watch_id = w_<url+goal 的 sha1 前10位>`（同一个 URL+目标只会有一条） |
| `GET /api/watches` | 列出 active 监控 + 实时算出 `next_run` |
| `POST /api/watch/{id}/run` | 立刻跑一次（演示不用等间隔） |
| `DELETE /api/watch/{id}` | 停止（软删，`status='stopped'`） |

**重启不丢配置**：启动时读 `page_watches` 表里 `status='active'` 的行，重新挂到调度器上。这里踩过一个坑：`BackgroundScheduler` 没有 `get_job_ids()`，要用 `{j.id for j in scheduler.get_jobs()}`——写错会导致 startup 直接失败、整个服务起不来（表现为 `ERR_CONNECTION_REFUSED`）。

**`page_watches` 表**：`watch_id`(PK) / `url` / `goal` / `minutes` / `created_at` / `last_run` / `last_page_id` / `runs` / `status`

**实测**：建一条 5 分钟监控 → `next_run` 正确；手动触发一次 + 间隔到点一次，两次都跑了（`runs=2`），`last_page_id` 更新，`pages` 表多出两条 20 行快照，最新那条带 3 张图。测试完已 `DELETE` 停掉，避免后台持续花 token。

> 成本提醒：一次监控执行 = 1 次摘要 + 1 次提目标 + 1 次 summarize + 最多 3 次 visualize，约 6 次大模型调用。演示期间建议 30~60 分钟一次，不用时点「停止」。

## 七之八、安全与限流（公网部署前置条件）

原则：**开放任意公网站点，只拦危险地址，不限制合法网站**。域名白名单只作为可选模式，不是默认策略——产品是"任意 URL 都能分析"，默认开白名单等于自废功能。

**`src/url_guard.py`：四道准入校验**

| 顺序 | 校验 | 拦什么 | 失败码 |
|---|---|---|---|
| 1 | 协议 | 只允许 http/https，拦 `file://`（读服务器本地文件）、`gopher://`（打内网的老武器） | `bad_scheme` |
| 2 | 端口 | 只允许 80/443/8080/8000/8443，拦 6379(Redis)/3306/22/9200 被当探针 | `bad_port` |
| 3 | 策略开关 | `PAGE_URL_POLICY=open`（默认，不限制域名）/ `demo`（仅 `PAGE_URL_DEMO_HOSTS`）/ `allowlist`（仅 `PAGE_URL_ALLOWLIST`） | `policy_demo` / `policy_allowlist` |
| 4 | 解析 IP 后判私网 | `getaddrinfo` 拿到全部 IP 逐个判 `0/8`、`10/8`、`100.64/10`、`127/8`、`169.254/16`（含云元数据 `169.254.169.254`）、`172.16/12`、`192.168/16`、`::1`、`fc00::/7` 等 | `private_ip` |

为什么必须解析成 IP 再判断：攻击者不会写 `127.0.0.1`，他会把 `evil.com` 解析到 127.0.0.1，只看字符串完全拦不住。

**重定向二次校验**：`crawl_any()` 拿到 `r.redirected_url` 后，如果落地地址和入口不同，再跑一遍同样的校验。不做这步，公网短链 302 到内网就能绕过前面所有检查。

**`src/rate_limit.py`：三层限流（保护钱包和机器，不是限制正常用户）**

| 维度 | 默认 | 环境变量 | 防什么 |
|---|---|---|---|
| 单 IP | 3 次/分钟 | `RL_IP_PER_MIN` | 一个人写脚本刷 |
| 单域名 | 5 次/分钟 | `RL_HOST_PER_MIN` | 把别人站打挂、单站重复烧 token |
| 全站每日 | 200 次/天 | `RL_DAILY_TASKS` | 零散来源合起来把 API key 刷爆 |

超限返回 **429 + `Retry-After` 头**，文案直接给人看："提交太频繁：同一来源每分钟最多 3 次，请 60 秒后重试"。实现是进程内 `deque` 滑动窗口 + 线程锁，单机部署零依赖；多实例时把 `_store` 换成 Redis 的 `INCR + EXPIRE` 即可，接口不动。

**顺序设计**：先 URL 校验（便宜、能给人话原因），再限流，**通过校验才计入额度**——被安全拦下的请求不该吃掉用户次数。

**接口**：`GET /api/security` 返回当前策略、允许端口、限流配置与当日用量，前端页脚直接展示。

**页面免责声明**（页脚常驻）：仅技术演示、版权归原站点、不留存内容镜像、遵守 robots 与频率限制、不抓需登录/付费内容、可联系删除。

**实测**

| 用例 | 结果 |
|---|---|
| `http://127.0.0.1:8000/` | 400 `该地址解析到内网/保留地址（127.0.0.1 → 127.0.0.1）` |
| `file:///C:/Windows/win.ini` | 400 `仅支持 http/https 协议的网址` |
| `http://books.toscrape.com:6379/` | 400 `该地址使用了非 Web 端口 6379` |
| `http://169.254.169.254/latest/meta-data/` | 400 私网拦截（典型 SSRF 目标） |
| `https://books.toscrape.com/` | 通过，正常出 20 行 + 图表 |
| 同一 IP 连发 4 次 | 前 3 次受理，第 4 次 **429 + Retry-After=60** |
| 6 个不同 IP 打同一域名 | 第 6 次被域名级限流拦下 |

## 七之九、Docker 打包与公网部署

**镜像结构**：`python:3.11-slim` + `fonts-noto-cjk`（图表中文不乱码）+ Playwright Chromium + 非 root 用户 `app`，`HEALTHCHECK` 打 `/api/health`。

**一个容器跑两个进程**：`entrypoint.sh` 后台起 `celery --pool=solo --concurrency=1`，前台 `exec uvicorn`。
原因是 DuckDB 只支持单进程写入，拆成两个容器会抢文件锁。等换 PostgreSQL 后才该拆成多容器 + 多 worker。

**compose 两个服务**：`redis:7-alpine`（`--appendonly yes --requirepass`，healthcheck 用 `redis-cli ping`）+ `app`（`./data:/app/data` 挂载、`shm_size: 1gb` 给 Chromium、`depends_on: service_healthy`）。

**容器内路径覆盖**：`.env` 里存的是 Windows 本机绝对路径（`D:\...`），compose 用 `environment:` 覆盖成 `DUCKDB_PATH=/app/data/crawl_data.duckdb` 等；`REDIS_URL` 用 `REDIS_PASSWORD` 拼成 `redis://:密码@redis:6379/0`。

**鉴权 `src/auth.py`**（HTTP Basic Auth，`PUBLIC_AUTH=1` 开启）：
`/api/health` 放行给探针；`PUBLIC_PASS` 为空时返回 503（宁可拒绝也不能"以为保护了其实是空密码"）；密码比对用 `secrets.compare_digest` 防时序攻击；401 带 `WWW-Authenticate: Basic realm="crawl-analyst"`。

**实测（8001 端口临时实例）**

| 请求 | 结果 |
|---|---|
| 无凭据 `/` | 401 `需要登录：请输入访问用户名和密码` |
| 无凭据 `/api/pages` | 401 |
| `/api/health` | 200（放行，容器 HEALTHCHECK 靠它） |
| `-u demo:test1234 /api/pages` | 200，返回 34 条记录 |
| 错误密码 | 401 |

**本机为什么不装 Docker**：无 Docker、无 WSL；装 Docker Desktop 要开 WSL2 + 重启 + C 盘占 1~2GB，而镜像最终跑在云服务器上，本机只需验证逻辑（已用同一套命令在本机 Python 环境跑通）。完整步骤见 `deploy/部署文档.md`。

**公网已实测（cloudflared 临时隧道，2026-11-17）**：本机 `D:\cloudflared\cloudflared.exe`（2026.11.0），
`start_public_demo.cmd` 一键拉起 Redis + worker + API + 隧道，拿到 `https://xxx.trycloudflare.com`。

| 公网请求 | 结果 |
|---|---|
| `/api/health` | 200 |
| `/` 无凭据 | 401 + `WWW-Authenticate: Basic realm="crawl-analyst"` |
| `/` 带 `demo:密码` | 200，页面 HTML 18097 字节 |
| `POST /api/page`（books.toscrape，"统计不同价格区间的商品数量"） | SUCCESS，20 行 + 1 张图，中文标题与坐标轴正常 |
| `/charts/page_xxx.png` | 200 `image/png` 40233 字节 |

**顺带修掉的泄露**：原来 `/api/task`、`/api/page/{id}` 会把 `D:\crawl_analyst\data\charts\...` 这种服务器绝对路径写进响应。公网接口不该暴露目录结构，已统一用 `page_svc.public_path()` 转成 `data/charts/xxx.png` 相对路径（前端只取文件名，行为不变）。

**Linux 中文字体**：`lida_svc.py` 改成运行时探测（`pick_cjk_font()` 遍历 `fontManager.ttflist`），Windows 命中「Microsoft YaHei」，容器里命中「Noto Sans CJK SC」（Dockerfile 装了 `fonts-noto-cjk`）。写死雅黑会在 Linux 上全变方块。

**本地无 Docker 时能验证到什么**：`docker-compose.yml` YAML 解析通过（2 service、端口/挂载/healthcheck 正确）；`entrypoint.sh` CRLF 数量 0（Linux 下可执行）；`from src.db import init_db`、`import src.main` 均成功；鉴权 4 组用例实测通过。**不能**验证的是：镜像 build 本身（依赖解析、Chromium 系统库）。

## 九、已知待处理问题

1. Windows 上跑 Celery 必须加 `--pool=solo`，否则报 `billiard` 相关错误；部署到 Linux 容器可换成默认并发。
2. `D:\_installers` 里是安装包残留（Git 57MB + Chromium 包 333MB + Redis 13MB），确认系统正常后可以删掉。
3. LIDA 的 `summarize` 目前返回的字段画像为空（`fields` 长度 0），不影响出图，后续做前端展示字段画像时再看。
4. 只解析列表页，未抓摘要页，所以还没有摘要文本可用于关键词/主题分析。
5. `has_code` 用关键词匹配，把泛指 "code" 也算进去，召回偏高（实测 9%）。
6. 月份由 `paper_id` 派生，跨月投稿有 1 天误差。
7. LIDA 生成的图表标题偶尔顶部被裁（`tight_layout` 不够），属于渲染细节，不影响数据。
8. 定时轮询已接入 APScheduler（见七之七）；URL 准入与限流已实现（见七之八）；仍缺反爬对抗（目标站封 IP 时的代理池）。
9. Docker 资产已写完（`deploy/Dockerfile`、`docker-compose.yml`、`Caddyfile`、部署文档），但本机无 Docker/WSL，**镜像 build 未在本机验证**；首次上云构建时按部署文档第 6 节排查。
10. 通用流程默认最多画 3 张图（`PAGE_MAX_CHARTS`），每个目标 1 张；一张图内多方案可以调 `per_goal`。
11. 通用抽取的"重复块"策略只覆盖**列表型**页面（卡片/文章/商品/帖子）；纯正文长文只能出"章节字数"类统计，属预期行为。
12. `news.ycombinator.com` 在本机网络下不可达（`ERR_CONNECTION_TIMED_OUT`），演示请用 books.toscrape / sspai / arXiv。
13. 监控结果只追加新快照，不做"和上次比差异"的告警；要做"变了才通知"就在 `_watch_job` 里比 `content_fingerprint()`。

# arXiv 采集数据清洗规则（v1）

> 这份文档解释 `src/crawl_svc.py` 里清洗代码到底做了什么、为什么这么做。
> 面试讲项目时，直接照这一份讲就够用。

## 一、数据从哪来

采集对象：arXiv 分类列表页，例如
`https://arxiv.org/list/cs.AI/recent?skip=0&show=100`

Crawl4AI 负责把页面抓回来，交给 BeautifulSoup 解析 `<dl id="articles">` 里成对出现的 `<dt>`（论文编号）和 `<dd>`（论文信息），提取出这些字段：

| 原始字段 | 来源 | 例子 |
|---|---|---|
| `raw_id` | `<dt>` 里的 `/abs/` 链接 | `2611.18543` 或 `2611.18543v2` |
| `title` | `div.list-title` | `Title: Imitation Bootstrapped Multi-Agent ...` |
| `authors` | `div.list-authors` | `Tony H. Zhang, Connor Mattson, Daniel S. Brown` |
| `comments` | `div.list-comments` | `9 pages, 5 figures. Code available at github.com/...` |
| `subjects` | `div.list-subjects` | `Artificial Intelligence (cs.AI); Machine Learning (cs.LG)` |
| `announce_date` | 分组的 `<h3>` 日期行 | `2026-11-16` |

## 二、为什么必须清洗（三类脏数据）

1. **格式噪声**：HTML 实体（`&amp;`）、零宽字符、连续空格换行、`Title:` 前缀、标题末尾句点。
   → 不清洗，后面按标题分组、算标题长度、做文本匹配全是错的。
2. **主键不规范**：同一篇论文会有 `v1 / v2 / v3` 多个版本，编号格式也可能异常。
   → 不做主键标准化，同一篇论文会被当成多篇，统计数据虚高。
3. **缺失与重复**：页面偶发缺标题/缺作者；同一篇论文同一天在不同分类下重复出现。
   → 不去重，趋势图和数量统计直接失真。

## 三、七条规则（全部是确定性规则，不调用大模型）

| 规则 | 做什么 | 怎么实现 | 为什么这么定 |
|---|---|---|---|
| **R1 文本规范化** | HTML 反转义、删零宽字符、压缩空白、去首尾空格、标题去句末句点 | `html_lib.unescape` + 正则 `[\u200b-\u200f\u202a-\u202e\ufeff]` + `\s+`→单空格 | 这些字符肉眼看不见，但会让“看起来一样的标题”变成两个不同值，影响去重和分组 |
| **R2 主键修正** | 去掉版本号 `v1/v2`，用正则 `\d{4}\.\d{4,5}` 校验；不合规整行丢弃 | `VER_RE.sub` + `PAPER_ID_RE.search` | arXiv 编号规则是固定的「YYMM.序号」，能直接反推提交年月；格式不符说明解析出错，宁可丢弃也不猜 |
| **R3 关键字段缺失** | `title` 或 `authors` 为空 → 整行丢弃 | 长度判断 | 这两列是所有分析的基础（趋势、字数、作者规模），缺了补不回来，也不该编造 |
| **R4 去重** | 同一 `paper_id` 只留一条，保留公告日期最新的一条 | `sort_values(announce_date)` + `duplicated(keep="first")` | 跨分类重复收录很常见；按数据本身的主键去重，比按标题模糊匹配更可靠 |
| **R5 类型转换与派生** | 作者数量转整数、月份由编号派生、标题长度整数、`has_code` 布尔 | `split(",")` 计数、`f"20{id[:2]}-{id[2:4]}"` | 数据库里存字符串没法算平均值和排序；月份从编号派生比爬页面日期更稳（列表页日期会随抓取时间变） |
| **R6 异常标记（只打标不删）** | 标题长度 <10 或 >250、作者 >30 人 → `is_flagged=True` | 布尔标记 | 这些是“真实但不典型”的数据（比如百人合作的大实验），删掉会丢真实信息，打标让后续分析可以选择排除 |
| **R7 派生特征** | `first_author`、`has_code`（comments 里出现 github/code） | 字符串切分 + 关键词匹配 | 这两列是最有分析价值的新特征：一作集中度、开源比例，都是能出结论的维度 |

## 四、清洗报告（可观测性）

每次清洗都会返回一份 `wash_report`，写进任务表并在前端展示：

```json
{
  "rows_in": 100,
  "dropped_invalid_id": 0,
  "dropped_missing_field": 0,
  "dropped_duplicated": 0,
  "flagged_atypical": 0,
  "rows_out": 100,
  "drop_rate": 0.0
}
```

意义：不用打开原始数据，就能知道这次采集的质量。如果 `drop_rate` 突然变高，说明页面结构变了或者解析规则失效——这是线上监控最重要的一条信号。

## 五、为什么清洗不用大模型（面试重点）

- 清洗是**规则问题**，规则问题用确定性代码解决：同样的输入必然得到同样的输出，可复现、可测试、零成本。
- 大模型适合做**语义问题**：给数据起个分析目标、解释趋势含义、写结论。LIDA 就只负责这一段。
- 如果让大模型清洗，一旦它改错一个字段，后面的统计全错，而且**无法审计**——这就是“幻觉污染事实数据”。
- 所以架构上是：确定性规则守住事实层，大模型只在解释层发挥作用。

## 六、当前实现位置

- 解析：`src/crawl_svc.py` 的 `parse_arxiv_listing()`
- 清洗：`src/crawl_svc.py` 的 `clean_papers()`
- 入库：`src/db.py` 的 `upsert_papers()`（`INSERT OR REPLACE`，靠 `paper_id` 天然支持增量更新）

## 七、已知局限（如实写进简历/答辩时要能说）

1. 只解析列表页，不抓每篇论文的摘要页；摘要文本分析（关键词、主题聚类）还没做。
2. `has_code` 是关键词匹配，会把 “code” 这种泛指也算进去，召回偏高（实测 9%，真实开源率会低于这个数）。
3. 作者切分按逗号，遇到带逗号的机构名会少数作者，误差很小但存在。
4. 月份从编号派生，月初投稿编号可能跨月，边界有 1 天误差。
